# Cards Domain — M5

## Contract and boundary

`contracts/openapi/customer.yaml` (1.5.0) is the single DTO contract. Frontend types are generated by `pnpm api:generate`; clients, services and UI only alias generated definitions. M5 adds card management through immutable action intents. No real authentication, merchant authorization/payment simulator, replacement, ordering, dispute, Agent or backend service is implemented.

| Endpoint                                     | Purpose                                                             |
| -------------------------------------------- | ------------------------------------------------------------------- |
| GET /customer/cards                          | CardSummary list under items                                        |
| GET /customer/cards/{cardId}                 | CardDetail with controls, version and updatedAt                     |
| POST /customer/card-action-intents           | Prepare an immutable action snapshot; 201                           |
| GET /customer/card-action-intents/{intentId} | Read exact terms and lifecycle status                               |
| POST /customer/card-actions                  | Execute intent reference with required Idempotency-Key; 200 receipt |
| GET /customer/card-actions/{actionId}        | Read completed action receipt, including after reload               |
| GET /customer/transactions?cardId=…          | M3 query extended with optional card attribution filter             |

## Card schemas and masking

- CardStatus: ACTIVE, FROZEN, EXPIRED, CANCELLED.
- CardType: DEBIT, CREDIT, VIRTUAL.
- CardScheme: VISA, MASTERCARD. Scheme names are text; there are no copied visual assets.
- CardSummary: id, displayName, maskedNumber, scheme, type, status and linkedAccount (id, displayName, maskedAccountNumber).
- CardDetail additionally returns four boolean controls, version and updatedAt.
- CardControls: onlinePayments, internationalPayments, atmWithdrawals, contactless.

The API only returns maskedNumber, such as `••8821`; it never returns full PAN, CVV or PIN. Linked account identifiers are already masked in the Mock layer. UI never receives full values to mask. The old Overview last4 field is replaced by the shared maskedNumber field.

Initial cards are Visa Debit `••8821` and Mastercard Credit `••1937`, both ACTIVE, linked to CNY Current. For the credit card this is its linked settlement account, not a new credit ledger. All four initial controls are ON. VIRTUAL, EXPIRED and CANCELLED are modeled without adding new cards or lifecycle operations. Expired/cancelled cards cannot prepare changes.

## Prepare, exact Review and explicit confirmation

CreateCardActionIntentRequest is a strict union:

- FREEZE / UNFREEZE: cardId and actionType only.
- UPDATE_CONTROLS: cardId, actionType and all four desired boolean controls.

Unknown fields, missing/non-boolean controls and control fields on freeze requests are rejected. UI drafts are local selections, not optimistic mutations. Preparing adds an intent resource without changing cards, accounts, transactions or clocks. Editing a proposed change means preparing another intent.

CardActionIntent includes id, status, actionType, card snapshot, before, after, riskDirection, authorizationRequirement, intentHash, createdAt and expiresAt. before/after are CardState objects containing status, all four controls and version. Prepared terms are immutable; only lifecycle status changes. SHA-256 binds the saved terms, including snapshots, classification, authorization requirement and expiry; lifecycle status is excluded. The hash is not a credential or authorization grant.

Review reloads this resource and displays exact before/after values for status and every control. The execute body accepts **only intentId and intentHash**. No replacement card parameters, controls or client assertion of authorization is accepted.

## Risk direction and authorization

Classification belongs to the Banking service, never React or a future LLM.

| Change                      | RiskDirection   | AuthorizationRequirement | M5 execution                            |
| --------------------------- | --------------- | ------------------------ | --------------------------------------- |
| ACTIVE → FROZEN             | PROTECTIVE      | CONFIRMATION             | Allowed after explicit confirmation     |
| Any control ON → OFF        | PROTECTIVE      | CONFIRMATION             | Allowed after explicit confirmation     |
| FROZEN → ACTIVE             | RISK_INCREASING | STEP_UP_AUTH             | Blocked                                 |
| Any control OFF → ON        | RISK_INCREASING | STEP_UP_AUTH             | Blocked                                 |
| Mixed ON → OFF and OFF → ON | RISK_INCREASING | STEP_UP_AUTH             | Blocked                                 |
| No effective change         | NEUTRAL         | CONFIRMATION             | Preparation rejected as NO_CARD_CHANGES |

Controls can be reviewed while a card is ACTIVE or FROZEN. Turning a control ON remains risk-increasing even while the card stays frozen. A frozen card does not make an increase in future capabilities safe to execute without verification.

STEP_UP_AUTH intents are prepared and reviewed normally. M8 adds Begin verification, a session-bound challenge and a short-lived single-use ActionAuthorization. Execution includes actionAuthorizationId and remains blocked without a valid grant for the original intent ID/hash. The service independently recomputes the risk requirement. See [Security API](security.md) for exact binding, atomic consumption and idempotency semantics.

## Idempotency, stale state and atomicity

Idempotency-Key follows M4's format: 1–128 ASCII letters, digits, underscores or hyphens. Successful keys are scoped to the card-actions endpoint within the demo session. Transfer keys have their own domain scope.

- Same key and intentId/hash returns the original receipt, even after expiry or later card changes.
- Same key with a different valid request returns 409 / IDEMPOTENCY_KEY_REUSED.
- An executed intent under another key returns 409 / CARD_ACTION_INTENT_ALREADY_EXECUTED.
- Failed validation does not consume a key or mutate the store.

The UI disables confirmation during processing and keeps the same key/reference for retry after an uncertain network result. The service provides the duplicate guarantee.

Immediately before a first execution, the service checks intent existence, expiry, hash, unexecuted status, card existence, exact current status/controls/version against before, and required authorization. A stale snapshot returns **409 / CARD_STATE_CHANGED**. Including version detects intervening changes even if the status/controls were later restored to the same values.

The service modifies a private state copy, then commits card status/controls/version/updatedAt, intent lifecycle, receipt and successful idempotency record in one synchronous store replacement. There is no await between revalidation and commit. Storage failure leaves state and clock unchanged. A receipt retains the exact completed change; it is not a promise that the card will never change again.

## Unified store, persistence and clock

Cards live in the existing MockBankingStore. `card-service.ts` contains business rules and `card-handlers.ts` only translates HTTP. Generic error/validation/hash helpers are shared with Transfers; the domain intent and receipt models remain separate.

The store uses sessionStorage key `aster-banking-state-v1` and schema version 5. Loading an existing M4 snapshot from `aster-m4-banking-state-v1` migrates card fields and transaction attribution while preserving balances, completed transfers, receipts and transfer idempotency. New writes use the shared key. To reset a local demo, remove both keys if present and reload. Tests reset the store before every case; no public reset or clock-control endpoint exists. Same-tab refresh is supported; cross-tab synchronization remains outside the simulator's guarantees.

Intent expiry uses the existing deterministic clock, initially `2026-09-27T10:30:00+08:00`, with a 15-minute simulated lifetime. A successful card action advances the clock by one second and uses that instant for card updatedAt and receipt timestamps. The clock is saved separately from the financial asOf so a reload preserves card-action time without falsely changing the financial snapshot. Real waiting does not advance demo time; tests can inject/advance/reset it.

## Cross-domain consistency and transactions

Freeze/control mutation never edits account balances, available funds, pending amounts, spending, wealth, historical transactions or pending transactions. Accounts responses remain identical. Overview changes only the affected card summary on freeze; its financial data/asOf remain unchanged. Control changes do not alter Overview financial data. Queries for Cards, Overview and action intents are invalidated after successful execution; unchanged transaction pages do not need invalidation.

Recent card activity uses M3 TransactionSummary and the existing query path. Optional cardId/cardMaskedNumber identify known attribution. Current-account card purchases, including pending Starbucks, are attributed to Visa Debit. Other historical sample records remain unattributed rather than inventing card ownership; their obsolete merchant card hints are removed during fixture initialization/migration. Mastercard has no attributed records in this selected history and shows an empty activity state.

cardId combines with account/date/status/type/category/search filters before pagination. The cursor signature includes cardId. Card mutations do not change transaction revision or cursor validity because no transaction has changed. Overview, AccountDetail and card activity all retain the same transaction objects. A successful M4 transfer still creates an unattributed BANK_TRANSFER and is unaffected by card freezing.

## Errors and UI states

| HTTP | Codes                                                                                                                                         |
| ---- | --------------------------------------------------------------------------------------------------------------------------------------------- |
| 400  | INVALID_REQUEST, INVALID_QUERY                                                                                                                |
| 403  | STEP_UP_AUTH_REQUIRED                                                                                                                         |
| 404  | CARD_NOT_FOUND, CARD_ACTION_INTENT_NOT_FOUND, CARD_ACTION_NOT_FOUND                                                                           |
| 409  | CARD_STATE_CHANGED, CARD_ACTION_INTENT_EXPIRED, CARD_ACTION_INTENT_HASH_MISMATCH, CARD_ACTION_INTENT_ALREADY_EXECUTED, IDEMPOTENCY_KEY_REUSED |
| 422  | CARD_NOT_ELIGIBLE, NO_CARD_CHANGES                                                                                                            |
| 500  | PERSISTENCE_UNAVAILABLE, INTERNAL_ERROR                                                                                                       |

Routes: `/app/cards`, `/app/cards/{cardId}`, `/app/cards/{cardId}/actions/review/{intentId}`, `/app/cards/{cardId}/actions/{actionId}`. Nested action routes also verify that the returned intent/receipt belongs to the route card. Lists/activity have loading, empty and error/retry states; details/review/receipts support loading, error/retry and resource-not-found states. Overview adds View cards without other layout redesign.
