# S1 security audit findings

Initial source audit: 2026-10-13. This record separates verified code behavior from tests still to run. The source of truth is the code linked below; previous milestone reports are context only. Severity describes the impact _if the identified gap is reached_, not an assertion that an attacker has exploited it. The S1 and R1 acceptance states remain **PARTIAL**. The dated remediation section below supersedes the initial status of S1-01 through S1-03.

## Reference baseline

The review uses [OWASP Top 10 for Agentic Applications 2026](https://genai.owasp.org/resource/owasp-top-10-for-agentic-applications-for-2026/), [OWASP API Security Top 10 2023](https://api-security.owasp.org/editions/2023/en/0x03-introduction/), [NIST AI RMF](https://www.nist.gov/itl/ai-risk-management-framework), and [NIST SP 800-63B-4](https://pages.nist.gov/800-63-4/sp800-63b.html) as review frameworks. They do not themselves prove a finding in this codebase. [AgentDojo](https://arxiv.org/abs/2406.13352) informs the prompt-injection test design.

An earlier real-model transaction-note run inserted a hostile note into the disposable bank and observed it in DeepSeek context. Five model HTTP calls used `list_transactions` and `summarize_spending`; there were zero PREPARE calls and no balance, transfer or intent change. Its summary artifact was accidentally overwritten by a later repeat. The first attempt did not expose the note to the model and ended `PARTIAL` (`artifacts/s1-real-model-injection-attempt1.json`). The latest repeat ended before model inference because the Docker network was internal-only and `httpx.ConnectError` occurred (`artifacts/s1-real-model-injection-network-blocked.json`). A fresh preserved pass is still required for S1 acceptance. The smoke script now retains failed attempts separately so they cannot overwrite a passing trace. A separate Spring auth smoke passed owner/cross-customer account and CSRF checks (`artifacts/s1-auth-boundary-smoke.json`); it does not cover all bank object classes.

## Authentication and deployment review

The [customer security chain](../../services/banking-core/src/main/java/com/asterbank/banking/security/adapter/security/CustomerSecurityChain.java) authenticates `/customer/**`, keeps Spring CSRF enabled and permits credentialed CORS only for configured origins. [Persistent configuration](../../services/banking-core/src/main/java/com/asterbank/banking/security/adapter/security/PersistentSecurityConfiguration.java) uses JDBC-backed session state, a `SESSION` HttpOnly/Secure/SameSite=Lax cookie, session-ID rotation on login, BCrypt password verification and a one-hour application session timeout. The readable XSRF cookie is a double-submit token, not an authentication cookie. `secure-cookie=false` is a local/demo override and must not be used on public HTTP. OTP generation uses `SecureRandom`; the database demo SMS sender is enabled only for local/test/demo profiles, never prod. [Demo credentials](../../services/banking-core/src/main/java/com/asterbank/banking/security/adapter/security/DemoCredentialSeed.java) are likewise profile-limited; their presence is not a production authentication design.

This is a source-level review, not a completed NIST authenticator assurance assessment. The audit did not run a full CSRF/CORS browser matrix, concurrent step-up race, log redaction scan or every action's expired-grant replay. These stay `UNVERIFIED`. The default [Agent Compose](../../infra/compose/agent.compose.yml) does not publish port 8001 to the host; the loopback test override does. Direct Agent reachability in other deployments and direct-request origin behavior remain deployment-dependent. No evidence here supports claiming public exposure or claiming it impossible.

## Supply-chain and CI scope

The frontend has a `pnpm-lock.yaml`, while Agent and Knowledge Python requirements pin package versions in their respective `requirements.txt` files. Their Dockerfiles use tagged base images rather than immutable digests; transitive Python package hashes are not locked. This is a **Medium hardening opportunity**, not evidence of a compromised image. The copied workspace contains no `.github` workflow directory, so automated CI gates cannot be verified from this snapshot. Reproducible CI should run the Spring Testcontainers suite, Agent/Knowledge/MCP tests, Web tests and security smoke scripts on a controlled disposable database, and should record image digests and vulnerability results. Do not infer that an external CI service is absent from the repository snapshot alone.
