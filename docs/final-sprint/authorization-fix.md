# Sprint 1 — 逐目标金融授权修复

2026-10-20。源码修复已通过确定性测试；最新镜像部署及真实 Spring 资金验收仍未完成。不得将下述脚本银行结果标为真实银行扣款验收。

## 原缺陷与修改

原 whole-turn amount veto 遇到“给张三转100元，再给李四转200元”会因为整句存在两个金额拒绝正常操作；同类金融回执此前按观察顺序分配给 Ledger 步骤。

现在 Planner 为每个金融步骤提供 `source_quote` 和 `tool_call.step_id`。这些是待校验的模型提案，不是授权。Runtime 的 `financial_terms.py` 验证：

- 来源是实际用户回合中的唯一连续片段；多笔同类操作的片段必须在原始目标中互不重叠、按原顺序出现。
- 金额安全检查针对该片段运行；原数值否决保留。金额、收款人、付款账户不能从另一目标借用。
- 收款人需有银行成功解析的查询依据，或经过验证的历史交易收款人依据；昵称、模型给出的 ID 不能相互证明授权。手机号只在 Runtime 保存规范化摘要，模型不接收该摘要。
- 明示的付款账户尾号、币种及备注必须对应当前条款。修改后沿用的收款人/账户必须对应之前已验证的绑定。
- “把刚才的100改成600”仅在旧金额确实是100、银行已取消旧意图且版本递增时允许校验通过。该校验不生成业务参数。错误旧金额、附加金额、未取消旧意图均拒绝。

银行 PREPARE 返回后绑定 `task_id / step_id / source_user_message_id / source_text_span / recipient_reference / account_reference / amount / currency / intent_id / terms_hash / execution_key / terms_version`。普通转账还核对银行返回的不可变快照。执行前重新检查绑定，执行后仅匹配完整五元组：

`step_id → intent_id → terms_hash → execution_key → receipt_id`

乱序、重复或伪造 step 的回执不能完成另一目标。取消保留旧记录并标记终态，不复活旧确认。记录通过既有 PostgreSQL JSON checkpoint 持久化，没有新增银行表或修改冻结 Customer API。

## 测试与边界

`tests/test_step_authorization.py` 共14项：独立100/200、金额/收款人互换、片段互换/合并/伪造、明确账户尾号、银行快照不符、执行键冲突、乱序/重复回执、检查点恢复、旧金额修订，以及完整两次独立确认的脚本银行 Runtime 流程。

最新 Agent 全量349项：339通过，10项环境跳过；这10项另在专用 PostgreSQL 数据库全部通过。新增绑定也完成真实 PostgreSQL 存取与回执匹配。金融业务适配器仍是脚本银行，不能据此宣布 AB01/AB02/AB08 的 Spring 资金条件通过。

仍有限制：同一多转账任务的局部条款修订可能被保守拒绝，需要用户完整澄清；中文大写/口语金额不在本次数字片段校验覆盖范围内。旧检查点若没有完整金融绑定，不从模型或回执顺序补造授权，应核实后取消/重新准备。必须在新镜像和可抛弃 Spring/PostgreSQL 中完成旧确认、双标签、提交后响应丢失等联测后，才开放本次新路径。
