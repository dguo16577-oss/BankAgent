# Aster Bank Agent 与 Web 改进计划

状态：**待实施**。制定日期：2026-10-01。目标是让本地比赛演示可重复、可解释、可由两位用户逐项验收；本文件不表示已完成下列工作。

## 1. 当前基线与边界

- Web、Spring Banking Core、PostgreSQL 和 Python Agent 已能在本机联通。Agent 可读取当前登录客户的部分银行信息、查询公开资料，并生成转账提案；转账仍由客户在既有银行页面审阅、验证和确认。双用户内部 Demo 转账已有隔离数据库的浏览器回归。
- 2026-10-01 已完成有限的带密钥 Web → Agent → DeepSeek 本机实测：模型参与账户问题的意图分类，并根据公开目录生成带产品引用的中文摘要。**超时、限流、失败回退和持续运行仍需系统验收**。页面的 `DeepSeek-assisted` 标记也可能仅表示模型参与了意图分类，不能解释为整段私人财务答复由模型生成。
- 已有 32 项[人工测试表](../testing/ai-banking-manual-checklist.md)，人工结果目前均待填写。既往自动化结果见[比赛演示交付报告](../milestones/competition-agent-demo-report.md)；本计划没有重跑全套回归。
- 银行卡和贷款申请目前止于**待审核**。真实发卡、授信、放款和跨行清算不在本计划中；Agent 不取得直接执行金融 mutation 或访问数据库的权限。
- Customer/Public OpenAPI 继续作为 Web 与银行业务的契约。是否扩展其冻结接口，需要单独的领域设计和验收，不能为了 Agent 对话方便而绕过。

## 3. 实施顺序

### 阶段 A：建立可复现基线（先做）

1. 保留现有 Demo 数据；用隔离测试库执行会改变资金的自动化场景。对[人工测试表](../testing/ai-banking-manual-checklist.md)逐项记录通过、失败或阻塞，尤其是登录、公开页、申请、Agent、双用户转账和中英文切换。
2. 为 G08 建立故障记录：访问地址、时间、浏览器网络响应、服务健康状态和所运行的构建版本。只有能复现的故障才进入修复清单。
3. 将[Agent 场景集调研与首版评测设计](../testing/agent-evaluation-scenarios.md)中的 36 个核心场景落实为隔离 fixture 和可执行测试：账户、消费、交易、公开产品、转账提案、模糊指令、越权指令、中英文以及后端不可用。每个样例写明预期工具、来源、拒绝或澄清行为。

**完成标准：** 32 项人工测试均有结果；每个失败项有复现步骤和负责人；所有后续工作使用同一基线场景集。

### 阶段 B：先修身份隔离与运行稳定性（P0）

1. 验证 G02；若旧客户消息在身份切换后仍可见，按认证身份给对话状态分区，且在登出、401、会话失效及身份变化时立即清空。补双标签/双用户浏览器测试。
2. 为 Agent 加入明确的就绪检查、请求超时与受控并发/限流；限制模型调用预算，日志仅记录关联 ID、意图、耗时和模式，不记录 Cookie、密钥、验证码或完整客户资料。
3. 固定本地密钥加载和重启步骤；使用用户本机的环境变量，不把密钥写入仓库、浏览器或 API 响应。在已完成的单次 DeepSeek 浏览器调用基础上，验证超时、限流、成本边界和无密钥回退。

**完成标准：** Alex/Lin 的对话在身份切换后不串线；无会话不能读取客户资料；模型成功时有可核验的模式与非敏感日志，模型失败时不编造余额或执行动作。

### 阶段 C：让 Agent 真正解决有限的银行问题（P1）

1. 将已支持意图整理为结构化任务：当前账户与余额、近期交易、指定周期消费、公开产品问答、转账提案、卡片/定期扣款页面指引。每类列出所需字段、可调用的只读工具、失败语义和引用来源。
2. 对转账引入显式澄清：多个同名收款人、多个可用来源账户、缺币种、金额歧义、不可用余额、停用收款人。只有唯一且合法的候选项才能生成提案；准备 intent 时仍由银行后端重新校验。
3. 将“模型分类”“模型生成公开摘要”“规则/银行 API 答复”分别展示。私有财务数据默认继续留在银行与 Agent 服务内；如未来要把经筛选的客户数据送给外部模型，须先单独决定同意机制、最小化范围、日志与删除规则。
4. 为每个支持意图加入正例、边界和对抗样例。模型不得选择任意 URL、HTTP method、客户 ID 或直接调用 mutation。

**完成标准：** 支持范围内的问题能给出有来源的答案或明确澄清；不支持的需求说明边界；自动化样例中没有未确认的资金变动、跨客户读取或编造产品费用。

### 阶段 D：Web 使用体验与内容质量（P1/P2）

1. Agent 对失败的问题提供一键重试、可理解的错误和重试后去重；长请求提供状态与取消。保留转账审阅页的金额、币种、收款人复核，不在聊天页设置一键扣款。
2. 对公开知识建立来源版本、更新时间和有限缓存；缓存失效后回源，过期或缺少明确条款时展示“资料不足”。为中文同义词、英文产品名、费用/资格问题建立检索评测集。
3. 逐页核对公开页、登录、申请、客户工作区和 Agent 的中英文、窄屏及空/错/加载态。对 G08 以真实后端场景验证申请提交后进入待审核及登录后返回原入口。

**完成标准：** 320、390、1440px 无横向溢出；失败后能重试且不重复发起业务 mutation；关键业务内容中英一致；公开事实都有有效来源，缺失条款不猜测。

### 阶段 E：演示打包与发布门槛（最后做）

1. 把 Python Agent 纳入本地 Demo Compose，提供健康/就绪检查、环境变量模板和可恢复的启动顺序；Next 同源代理只访问配置的 Agent 地址。保留无密钥确定性模式作为可演示的降级路径。
2. 运行 `pnpm contract:check`、`pnpm lint`、`pnpm typecheck`、`pnpm test`、`pnpm build`、Agent 单元测试、Java `clean verify`、Mock/真实后端/容器 E2E。双用户测试使用独立浏览器上下文和临时 PostgreSQL，核对提案前余额不变、确认后双边记账及幂等。
3. 更新人工测试表、演示脚本、截图和已知限制。公网发布另以最新镜像的漏洞处置、HTTPS、密钥管理和运维验收为放行条件；**本计划本身不批准公网部署**。

**完成标准：** 一条可重复的启动路径能同时提供 Web、Banking Core、PostgreSQL、Agent；手工和自动化结果能相互核对；发布门槛有逐项证据。

## 4. 每阶段必须守住的约束

- 客户身份只来自 Spring Session；Agent 只通过 Banking API 获取授权数据，不直接访问 PostgreSQL。
- 任何资金、卡片或投资 mutation 都留在既有银行授权流程，用户必须看到最终审阅并主动确认。Agent 生成的内容不能成为授权凭证。
- 金额仍用 decimal string/精确数值；客户间数据隔离、CSRF、Step-Up、幂等和服务器端掩码不能被 AI 功能绕过。
- DeepSeek key 只在 Agent 进程环境中；对外模型默认不接收原始聊天、密码、验证码、Cookie 或客户银行数据。模型输出是候选解释，银行 API 和校验规则决定事实与行动。
- 待审核申请不宣传为已审批、发卡或放款；公开产品摘要不能冒充完整费用和资格条款。

## 5. 建议的验收演示

在隔离浏览器会话分别登录 Alex 和 Lin：Alex 向 Agent 查询本人账户 → 询问带来源的公开产品问题 → 请求“转给 Lin Wei 10 元” → 在原银行转账页复核、验证并确认 → Lin 刷新账户与交易看到入账 → 再测试模糊收款人、无会话、服务故障、模型回退与语言切换。演示记录应包含模式标记、回执和关键页面截图；不要用同一浏览器的两个 localhost 端口假装隔离会话。
