The current ProductApplication response always maps status to `SUBMITTED`. It never approves or issues a card. Existing card controls are persisted, but the repository has no card-payment or ATM authorization endpoint where those controls could affect a live transaction. Account transfers are not card transactions. Therefore M21 must not claim that toggling a control blocks a nonexistent card payment path.

## Compatibility proposal requiring one approval

All changes below are **additive** to current Customer OpenAPI and use new Flyway migrations. They do not edit V1–V26, remove endpoints, or change existing completed actions. The exact schema names should follow current generation conventions.

1. **Intent cancellation.** Add owner-scoped `POST /customer/card-action-intents/{intentId}/cancel` and `POST /customer/application-intents/{intentId}/cancel`, with reason enum `USER_CANCELLED | TASK_REVISED | TASK_FAILED | MAX_STEPS_EXCEEDED`. Add `CANCELLED` to corresponding intent status. Lock the same intent row used by execution; cancelled intents cannot execute or revive. This is necessary before Agent PREPARE tools can safely support revision or user rejection.
2. **Formal lost status.** Add `REPORT_LOST` to card action type and `REPORTED_LOST` to card status. Allow `ACTIVE/FROZEN → REPORTED_LOST`; ordinary `UNFREEZE` only allows `FROZEN → ACTIVE`. Report-lost requires a review intent and step-up. A lost card stays unusable; replacement issuance is out of scope and must not be claimed.
3. **Self-service limits.** Add `perTransactionLimit` and `dailyLimit` CNY money fields to card state and a `UPDATE_LIMITS` card action variant. The existing card intent should bind before/after limits, version, hash and expiry. Bank rules reject negatives and policy-max exceedance. Decreasing limits is protective; increasing them is risk-increasing and requires step-up. Add an internal card-authorization policy that checks status, four control switches and limits against a persistent daily usage ledger. Until a card authorization/transaction path uses that policy, present limits as configuration only and mark live enforcement unavailable.
4. **Credit-limit application.** Add a separate `CreditLimitApplication` and immutable prepare intent rather than treating user-configurable spending limits as bank credit. Customer routes: prepare, cancel, submit, list, detail. Bind card, current credit limit, requested CNY limit, customer, session, terms/hash, expiry and idempotency key. Submission writes `SUBMITTED` (or `UNDER_REVIEW` if a real reviewer takes it); there is no automatic increase or approval in M21. Approval remains a separate bank-owned future operation.
5. **Application status.** Preserve existing initial-card application intake. A new review-status transition mechanism, if introduced, must be bank-owned; the Agent only reads status and may not set `APPROVED` or create a card. Keep `SUBMITTED` as the truthful status while no reviewer exists.

Suggested migrations: V27 for card action/application cancellation and lost status; V28 for card limit state/usage; V29 for credit-limit application intents and applications. Each uses FK/UNIQUE/CHECK constraints, owner indexes, intent status/expiry indexes and idempotency records. Add tests for row-lock races, old-intent invalidation, stale version, cross-customer access, lost-card unlock rejection, policy max, step-up and duplicate execution. The API freeze manifest, generated types and implementation matrix must be updated with each compatible increment, then checked with `pnpm contract:check`.

## Non-blocking work completed

The Agent now exposes six additional **read-only** tools: `get_card_controls`, `list_card_products`, `get_card_product`, `compare_card_products`, `list_card_applications`, `get_card_application`. Total visible registry: **35 tools**, with no execute method. Product descriptions and application display text are untrusted observations. Canonical card, product and application IDs must first come from an observed list. The bank still owns card and application state. Agent tests pass **208/208**. Real DeepSeek read-only traces: [`artifacts/m21-read-deepseek-traces.jsonl`](../../artifacts/m21-read-deepseek-traces.jsonl), four successful cases, no mutation.
