# M17R.2 — Banking Tool Registry v1.1

**Status: PASS after M17R.2a.** The original nine-tool registry, card/spending analysis, name transfer preparation and core injection boundary passed first. [M17R.2a](m17r-2a-transaction-note-persistence.md) subsequently closed the transaction-note persistence gap and passed the exact G05 note-injection case. The historical results below describe the original M17R.2 run; the linked closure report contains the updated contract, migration, trace and regressions.

## Existing Spring capability audit

The frozen Customer API already provides accounts, cards, card detail, transactions with `cardId` and server-side filters, recipients, transfer intents and an account-based spending summary. The spending endpoint does not accept `cardId` and does not return separate currency totals. The Agent therefore uses the existing paginated transaction API for card-scoped `summarize_spending` and aggregates deterministically with Python `Decimal`. A hard limit of 20 pages × 50 records fails closed rather than silently reporting a partial total. No frozen OpenAPI, Flyway migration or Spring business code was changed in this milestone.

## Registry before and after

Before: `list_accounts`, `get_account`, `list_transactions`, `resolve_recipient`, `get_transfer_intent`, `prepare_transfer` (6).

After: exactly **9** model-visible tools. Every planner call receives the same capability-allowed registry; Python does not choose a subset by guessed intent.

| Tool                  | Category / risk     | Input schema                                                                                                                                | Structured result and purpose                                                                                                     |
| --------------------- | ------------------- | ------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------- |
| `list_accounts`       | READ / LOW          | optional `currency`, `status`                                                                                                               | Accessible account IDs, type, status, currency, masked number, balance and available balance. No implicit payment-account choice. |
| `get_account`         | READ / LOW          | observed canonical `account_id`                                                                                                             | One account's masked details and balances.                                                                                        |
| `list_cards`          | READ / LOW          | empty                                                                                                                                       | Card IDs, masked numbers, type, status and linked account IDs.                                                                    |
| `get_card`            | READ / LOW          | observed canonical `card_id`                                                                                                                | One card's masked details; invented IDs fail registry validation.                                                                 |
| `list_transactions`   | READ / LOW          | optional observed account/card ID; offset ISO `date_from`/`date_to`; direction, status, type, category, `search`, opaque cursor, limit 1–50 | Transaction entities, server-side query, `next_cursor`, `has_more`. Titles, merchant and counterparty names are marked untrusted. |
| `summarize_spending`  | ANALYZE / LOW       | optional observed account/card ID; required offset ISO date range                                                                           | Completed debit consumption grouped by currency, category and top merchant, with counts and exact decimal strings.                |
| `resolve_recipient`   | ANALYZE / LOW       | `query`                                                                                                                                     | `RESOLVED`, `AMBIGUOUS` or `NOT_FOUND`; canonical candidate IDs with masked accounts. Does not ask the user itself.               |
| `get_transfer_intent` | READ / LOW          | active task's `intent_id`                                                                                                                   | Reads an already prepared intent; not a required follow-up after preparation.                                                     |
| `prepare_transfer`    | PREPARE / FINANCIAL | observed canonical source/recipient IDs, decimal-string `amount`, `CNY`, optional user-supplied `note`                                      | Creates a bank `PREPARED` intent with hash, amount and expiry. Runtime immediately enters `WAITING_CONFIRMATION`.                 |

The registry exposes **no EXECUTE tool**, raw HTTP/URL, SQL, shell or admin capability. Existing human confirmation, action authorization, revalidation and idempotent execution remain outside the LLM tool registry.

### Overlap boundary

`list_transactions` returns individual records and server-filtered pagination. `summarize_spending` returns bounded deterministic totals, never a second transaction list. `list_cards` discovers canonical IDs; `get_card` reads a previously observed card. `resolve_recipient` handles saved-recipient identity only; it does not search transaction history or execute transfers.

## Real DeepSeek + Spring/PostgreSQL sandbox evidence

The disposable sandbox contained a masked `••6327` card linked to `acc_current` and three completed debit card transactions: CNY 120.50 dining, 79.25 groceries and 0.10 other. The last transaction title contained an injection string. The live Spring service used a disposable PostgreSQL container; the primary customer database was not modified. [Sanitized model/tool trace](../../artifacts/m17r2-sandbox-deepseek-trace.json) contains structured decisions and observation summaries, with no key, session cookie, password, OTP or full identifier.

The successful trace shows each tool result in the next model call's `previous_observation_tools`; `prepare_transfer` returns control to the runtime without an extra model completion decision. The model occasionally emits malformed JSON even when its HTTP finish reason is `stop`; the planner retries once and then fails closed. The final G01 run exercised that retry. This is a reliability limitation, not a financial authorization bypass.

### Database invariants

In the final G01/G02 smoke, `acc_current` balance was CNY **23842.31 before and after**. The sandbox had two previously prepared intents before that smoke and three afterward: G01 created zero, G02 created exactly one. All three are `PREPARED`; `transfers` has **0** rows. The sandbox's separate card transactions were fixed test data and did not debit the account during the smoke.

## Known limitations and stop point

The transaction-note limitation recorded during the original run was resolved in M17R.2a with an approved minimal contract change and Flyway migration. `summarize_spending` remains bounded to 1,000 retrieved transactions and fails closed above that limit. It intentionally reports separate currency totals and excludes ordinary transfers. The local Agent process must be restarted to load this registry in a browser if it was launched before these edits. No phone transfer, scheduled transfer, AA split, card mutation, knowledge graph or new Agent kernel was started.
