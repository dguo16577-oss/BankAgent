## Source and index inventory

The source is the repository's authored demo public content (`services/banking-core/src/main/resources/demo/public-content.sql`): 21 public catalog items and 15 public support articles. All 36 are labelled **Aster Demo Policy**, not real-bank terms. The indexed content covers BANK_ACCOUNT, TRANSFER, CARD, WEALTH, SPENDING, SUBSCRIPTION, SECURITY and GENERAL_FAQ. The isolated PostgreSQL acceptance database held 36 documents, 36 versions and 156 chunks; reimporting the same source was skipped. Banking transactions and customer-private material were not indexed.

Flyway V34 creates `knowledge.documents`, `document_versions`, `document_chunks` and `ingestion_jobs` in a separate schema. Each version retains content, SHA-256, effective dates, status and source URI; chunks retain heading and line location. The import pipeline supports reviewed local Markdown, TXT, HTML and PDF manifests, validates source paths and URI schemes, and records job failures. It does not publish arbitrary uploaded text. The selected PostgreSQL 17 Alpine image has no pgvector extension, so this bounded demo stores E5 vectors in `REAL[]` and ranks at most 5,000 prefiltered candidates in the service. Full-text and trigram indexes support lexical candidates. See [K1 architecture](../architecture/banking-knowledge-base.md) and [K2 architecture](../architecture/hybrid-rag.md).

## Retrieval and Agent boundary

The service performs PostgreSQL-side PUBLIC, effective-version, category and product filtering, then combines full-text, trigram, exact-term and multilingual E5 cosine rankings through reciprocal-rank fusion. Responses contain an evidence ID, source URI, title, version, effective status, heading, line location and score. It is an internal, read-only service. Customer-scoped retrieval is disabled; the SQL predicate excludes CUSTOMER rows even if they exist in the database.

Agent v2 has one new read-only tool, `search_bank_knowledge`, bringing its visible registry from 49 to 50. Existing banking tools, ActionIntent, confirmation, step-up, policy and Spring execution are unchanged. Model-selected knowledge arguments do not grant authority: the tool has a fixed internal endpoint, observations are `UNTRUSTED_EXTERNAL_DATA`, and a read-only user request cannot become a financial PREPARE because of retrieved instructions. The runtime checks knowledge citation IDs against observed evidence and retries a malformed citation once before failing closed. AG-UI source cards are built from observations; a cited UUID is preserved through presentation masking only if that exact ID was observed. A user still sees the legacy `/app/agent` alongside the CopilotKit experiment.

One browser failure exposed a model-selected `WEALTH` filter for a savings question. The category and product filters are now described as optional hard filters, omitted unless the user names an unambiguous scope. A subsequent browser answer retrieved _Flexible Savings_ and cited the variable, non-guaranteed illustrative interest text. A risk-profile answer also added an unsupported human label to the observed `R2` code; after a Planner instruction change, the same browser question correctly said the available evidence did not define that mapping. Both earlier failures remain in the browser record. For two named products, the Planner is now told to search each product separately if the first result set lacks either source. The two underlying searches hit the correct products, but a real-model comparison has not passed after the upstream HTTP 402.

## Evaluation evidence

The 28-case specification and independent expected source/behavior are in `services/knowledge-service/eval/cases.json`. Its executable retrieval subset passed **23/23** (`artifacts/k2-retrieval-results.json`). KB24 now checks two product-specific searches and requires both sources. Five cases concern answer abstention, injection/isolation or ordinary bank tool choice; the retrieval harness deliberately labels them `NOT_RUN_IN_RETRIEVAL_HARNESS` instead of inflating retrieval recall. KB21 and KB22 abstention, and KB26 retrieved-text injection, passed in a separate real-model run. KB27 passed the private-row SQL exclusion test, and KB28 passed the ordinary-transfer smoke without knowledge search. Thus observed retrieval Recall@5 for the retrieval subset is 23/23; it is not an estimate on a production corpus. The earlier warm retrieval p95 was about 44 ms; a cold model load dominated the earlier 553 ms mean.

The isolated real DeepSeek trace (`artifacts/k2-real-deepseek-smoke.json`) recorded **8/8 expected task states**: seven knowledge or bank-plus-knowledge answers succeeded with observed citations, and an ordinary Lin Wei transfer used `resolve_recipient`, `list_accounts`, `prepare_transfer` and stopped at `WAITING_CONFIRMATION` without calling RAG. The risk-profile case called both the bank tool and knowledge search. Account balances were unchanged. The eight tasks used 18 planner calls, 277,978 prompt tokens and 2,336 completion tokens; usage coverage was complete. Average end-to-end latency was about 7.9 s, with the bank-plus-knowledge case about 27 s. The existing M18 peak-rate snapshot estimates USD 0.06613874 for those responses; this is not a billing receipt. The three separate answer/security tasks used 94,036 prompt and 1,068 completion tokens, estimated USD 0.02271864, with unchanged balances. One intermediate KB21 run failed closed on a tool validation error, then passed on rerun; the failed attempt is not counted as a pass.

Eight distinct natural-language cases were answered in a real Chromium session at `http://localhost:3002/app/agent-copilot`: savings rate, lost card, transfer failures, step-up, card annual fee, actual risk rating plus policy, available-versus-book balance, and bank direct debit versus merchant membership. Their answers contained observed citations and the UI rendered source cards. A focused browser retest confirmed that a UUID citation ending in a long numeric run stayed intact after AG-UI masking; a second risk-profile retest removed the unsupported `R2` label. The trace is `artifacts/k2-browser-acceptance.json`. It also preserves an earlier failed request during cold startup, a wrong-category abstention, and one failed subscription attempt after a long thread; retrying the subscription question in a fresh authenticated browser session succeeded. A later two-product comparison failed closed because DeepSeek returned HTTP 402. These failures mean the browser acceptance is exploratory, not a claim that long-thread reliability is solved.

The available automated safety checks cover allowlisted ingestion, private-row SQL exclusion, historical-versus-current version selection, untrusted tool observations, forbidden extra URL arguments, citation masking, and existing Agent financial guards. In KB26 a deliberately hostile source was observed by the real model, which treated its transfer instruction as untrusted data: no PREPARE decision and no balance change. The injected row was removed after the test; the knowledge inventory returned to 36 documents. Citation correctness in the runtime is an ID-membership check; it does not prove each sentence is entailed by the cited paragraph. Manual browser review found and corrected one unsupported risk-code interpretation, so automated answer groundedness remains an open quality gap. No unexpected financial mutation was observed in the real-model tasks. The transfer intent in KB28 was prepared but never confirmed.

## Limits and next boundary

The first corpus is English-authored simulated public material with selected Chinese product aliases. There is no customer-private RAG, no production policy approval workflow, no ANN vector index and no sentence-level entailment checker. The current service liveness check starts only after the local embedding model is loaded; model installation must be completed at build/deploy time. On this Windows host, loading E5 in a second Python process while the service also holds the model caused a native Torch access violation during evaluation; the same harness passed after the service was stopped. The demo browser proxy used for same-origin acceptance is test infrastructure, not a production deployment specification. Dynamic two-product citation behavior and long-thread success still need a real-model rerun when the DeepSeek account accepts requests; HTTP 402 indicates a provider-side payment/access response, not a verified diagnosis of its cause.

MCP could later expose the same read-only search capability through a separate permissioned adapter. It must preserve the server-side PUBLIC/identity filter and cannot expose SQL, arbitrary URLs or financial execution. This milestone stops before MCP and SFT.
